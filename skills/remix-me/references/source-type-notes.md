# Source-type notes

Read only the sections matching the supplied references.

## Repositories

Check the stated license, revision, README, architecture/docs, package manifests, public entry points, tests, examples, and release/maintenance signals. Prefer behavior demonstrated by tests or runnable examples over README claims. Record language/runtime assumptions and identify the smallest transplantable concept rather than copying a whole subsystem.

## Papers and technical reports

Separate the contribution from background and speculation. Capture assumptions, objective, algorithm steps, data requirements, complexity, baselines, metrics, ablations, failure cases, and whether artifacts reproduce the claim. Compare the method against existing local behavior and explain what evidence would be needed to establish a local improvement.

## Documentation and blogs

Mark publication date and likely staleness. Distinguish normative instructions, measured results, opinion, and illustrative snippets. Verify APIs or commands against the current target repository before proposing adoption.

## Webpages and UI references

Describe information architecture (navigation, grouping, hierarchy), content style (tone, density, terminology), visual tokens (spacing, type scale, color, contrast), interaction states, and responsive/accessibility behavior separately. Classify each desired change as inspiration, local reimplementation, or reuse of code/assets. Check copyright, trademark, and accessibility implications; visual similarity alone is not evidence of usability.

## Other artifacts

State how the artifact was parsed, what was observable, and what could not be verified. Preserve hashes or filenames when reproducibility matters, and avoid treating generated output as authoritative source code without provenance.
